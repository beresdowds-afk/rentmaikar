# Backend Handoff Package: API Contract, Spec & Credentials

Goal: produce everything a separate backend team needs to take ownership of Rentmaikar's server surface — a complete written API contract, a machine-readable OpenAPI spec, an env template, and a credentials inventory with a rotation/ownership plan. No values of any secret are ever written into these files.

## What gets produced

All under a new `docs/handoff/` folder, plus a downloadable zip in the documents area.

### 1. API contract (`docs/handoff/API-CONTRACT.md`)
Covers the whole server surface — the Express gateway plus all 161 Supabase edge functions — grouped by domain:

- Gateway routes: `/api/health`, `/api/health/diagnostics`, `/api/domains`, `/api/cpaas/*`, `/api/webhooks/*`
- Edge functions grouped as: Auth & Identity, Payments (PayPal/Paystack/OPay), Communications (Sent/Twilio/Termii/Resend), Email queue & webhooks, VoIP & IVR, IoT/Telemetry (Hologram, Traccar, EMQX, Sarekon), Persona KYC, Notifications & events, Scheduled/cron workers, Admin operations, AI/ElevenLabs.

For each endpoint: method, path, purpose, auth mode (public / JWT / cron-token / provider-signature), request shape, response shape, side effects, and which secrets it reads. Each entry is derived by reading the function source, not assumed.

### 2. Machine-readable spec (`docs/handoff/openapi.yaml`)
OpenAPI 3.1 covering the same surface: gateway paths at `https://staging.rentmaikar.com`, edge functions under the functions base URL, security schemes (bearer JWT, `x-cron-token`, provider HMAC headers), and request/response schemas. Validated with a spec linter before delivery.

### 3. Env template (`docs/handoff/backend.env.template`)
Every env var the server side reads, with `NAME=` left empty, grouped by provider, annotated with required/optional and which functions consume it. Generated by scanning `Deno.env.get(...)` and `process.env.*` across all functions and the gateway, so nothing is missed and nothing stale is carried over.

### 4. Credentials inventory & rotation plan (`docs/handoff/CREDENTIALS.md`)
A table per credential: name, provider, purpose, where the backend team obtains/rotates it, current owner, sensitivity, and rotation cadence. Plus a handover sequence: which provider consoles must be transferred, the order to rotate in so live traffic isn't dropped (webhook secrets before endpoint cutover, messaging keys during a low-traffic window), and the verification step after each rotation. No secret values are included.

### 5. Cutover notes (`docs/handoff/CUTOVER.md`)
Domain topology (frontend `rentmaikar.com`, backend `staging.rentmaikar.com`, inbound mail `backend.rentmaikar.com`, outbound mail `notify.rentmaikar.com`), the webhook URLs each provider must be repointed at, the frontend's single integration seam (`src/lib/backend-client.ts`), cron/scheduled job list, and a post-cutover smoke checklist.

### 6. Delivery
A zip of `docs/handoff/` written to the documents area so it can be downloaded and shared.

## Technical notes

- The env scan is scripted (ripgrep over `supabase/functions/**` and `backend/src/**`) so the template and credentials table stay exhaustive and reproducible.
- Auth mode per edge function is read from its source (JWT verification in code, `verify_cron_token`, HMAC signature helpers in `_shared/`), not inferred from naming.
- Scheduled workers are cross-checked against pg_cron job definitions so the backend team knows what runs unattended.
- Read-only work: no source behaviour changes, no migrations, no secret creation or rotation performed. Rotation is documented for the backend team to execute.
